# Kong demo certificates

Self-signed CA hierarchy and leaf certs used by the kongpose stack. Everything is generated by [`smallstep/step-cli`](https://smallstep.com/docs/step-cli/basic-crypto-operations) wrapped in a small bash script.

## Quick start

```sh
cd ssl-certs/smallstep
./renew_certs.sh
```

The script:

1. Checks whether `kong.lan.pem` is valid for more than 30 days. If yes, exits — nothing to do.
2. Backs up the existing `*.pem` / `*.key` files to `ssl-certs/.cert-backup-YYYYMMDD_HHMMSS/`.
3. Regenerates any CA in the chain whose own expiry is inside the grace period.
4. Regenerates **all** leaf certs, signed by Intermediate CA 2.
5. Builds `combined-wild.pem` for HAproxy.
6. `chmod 644`'s everything so the Kong containers can read the keys.
7. Offers to `docker compose restart` the cert-consuming containers that are currently running.

The script is idempotent and safe to re-run.

## What gets generated

| File | Purpose | CN | Notable SANs |
|---|---|---|---|
| `root_ca.pem` / `.key` | Self-signed root | Demo Kong Root CA | — |
| `intermediate_ca1.pem` / `.key` | Signed by root | Demo Kong Intermediate1 CA | — |
| `intermediate_ca2.pem` / `.key` | Signed by int1, signs all leaves | Demo Kong Intermediate2 CA | — |
| `kong.lan.pem` / `.key` | Admin API, Manager, Portal, Portal API, Proxy SSL | `manager.kong.lan` | all `{manager,api,portal,portal-api,proxy,bare}.{kong.lan,kong.com}` + `127.0.0.1` |
| `wild.kong.lan.pem` / `.key` | Wildcard (keycloak, solace) | `*.kong.lan` | `*.kong.lan`, `*.kong.com`, `127.0.0.1` |
| `client.kong.lan.pem` / `.key` | mTLS client | `client.kong.lan` | `127.0.0.1` |
| `client/mtls-consumer.kong.lan.pem` / `.key` | mTLS consumer identity | `mtls-consumer` | `127.0.0.1` |
| `combined-wild.pem` | HAproxy bundle (`wild + int2 + int1 + root + key`) | — | — |

## Configuring

Edit the variables at the top of [`smallstep/renew_certs.sh`](smallstep/renew_certs.sh):

```bash
DOMAINS=(kong.lan kong.com)             # add/remove TLDs — all certs cover all listed domains
KONG_PREFIXES=(manager api portal portal-api proxy)
EXTRA_SANS=(127.0.0.1)                  # IPs or extra hostnames added to every leaf

GRACE_DAYS=30                           # auto-renew if expiring within N days
ROOT_CA_HOURS=87600                     # 10y
INT1_CA_HOURS=43800                     # 5y
INT2_CA_HOURS=26280                     # 3y
LEAF_HOURS=8760                         # 1y

STEP_IMAGE="smallstep/step-cli:0.28.6"  # pin a known-good version
```

The CA hierarchy uses `step` templates (`root.tpl`, `intermediate1.tpl`, `intermediate2.tpl`) to set `maxPathLen` constraints so a 3-level chain validates correctly. The script writes any missing templates on first run.

### Name constraints on the root CA

`root.tpl` includes a critical `nameConstraints` extension limiting the entire chain to the domains in `DOMAINS` plus loopback IPs (`127.0.0.0/8`, `::1/128`). This is important: when you import `root_ca.pem` into your OS truststore, the constraint stops the CA from being able to sign valid certs for arbitrary domains — even if the root key leaks, the blast radius is just `*.kong.lan` / `*.kong.com` / loopback.

The script regenerates `root.tpl` from the current `DOMAINS` array each run. **If you change `DOMAINS`, you must delete `root_ca.pem` (and both intermediates) and re-run the script** to actually issue a new root cert that reflects the new constraints — the script will print a warning when this is needed. Don't forget to re-import the new root into your OS truststore afterward.

Compatibility: macOS Keychain, Chrome, Firefox, and modern Java all enforce `nameConstraints`. A few legacy clients (older Java, some embedded TLS stacks) ignore it — for a local dev demo this is irrelevant.

## Trusting the CA

For browsers to accept the certs, your OS keychain must trust `root_ca.pem`. The intermediates are presented in the chain, so they don't need to be imported — but doing so doesn't hurt.

**macOS:** double-click `root_ca.pem`, then in Keychain Access set it to "Always Trust".

![OSX keystore](/images/import-ca-cert.png)

**Linux (Debian/Ubuntu):**
```sh
sudo cp root_ca.pem /usr/local/share/ca-certificates/kong-demo-root.crt
sudo update-ca-certificates
```

**Firefox:** uses its own trust store. Preferences → Privacy & Security → Certificates → View Certificates → Authorities → Import.

## Verifying a cert

```sh
openssl x509 -in smallstep/kong.lan.pem -noout -subject -issuer -ext subjectAltName -enddate
```

You should see something like:

```
subject=CN=manager.kong.lan
issuer=CN=Demo Kong Intermediate2 CA
X509v3 Subject Alternative Name:
    DNS:manager.kong.lan, DNS:api.kong.lan, DNS:portal.kong.lan,
    DNS:portal-api.kong.lan, DNS:proxy.kong.lan, DNS:kong.lan,
    DNS:manager.kong.com, DNS:api.kong.com, DNS:portal.kong.com,
    DNS:portal-api.kong.com, DNS:proxy.kong.com, DNS:kong.com,
    IP Address:127.0.0.1
notAfter=...
```

To confirm the root's name constraints are in place:

```sh
openssl x509 -in smallstep/root_ca.pem -noout -ext nameConstraints
```

You should see `Permitted: DNS:kong.lan, DNS:kong.com, IP:127.0.0.0/8, IP:0:0:0:0:0:0:0:1/128` (or similar).

## Permissions note

Step writes keys at 0600 by default. Kong runs as a non-root user inside the container, and the host uid almost never matches the container's kong uid. The script's chosen workaround is to `chmod 644` every key — fine for a local demo, **never** do this in production. The proper fix is to export `KONG_USER=$(id -u):$(id -g)` so the container runs as your host uid and can read your 0600 keys; the compose file already supports this via `user: "${KONG_USER:-kong}"` on `kong-cp`.

## Manual reference

If you'd rather generate certs by hand (e.g. one-off cert with custom SANs), the underlying `step` commands are below. Run from the kongpose repo root.

### Root CA

```sh
docker run --rm \
  -v $(pwd)/ssl-certs/smallstep:/tmp \
  smallstep/step-cli:0.28.6 step certificate create \
  --template /tmp/root.tpl --not-after=87600h \
  --no-password --insecure \
  "Demo Kong Root CA" /tmp/root_ca.pem /tmp/root_ca.key
```

### Intermediate CA 1 (signed by root)

```sh
docker run --rm \
  -v $(pwd)/ssl-certs/smallstep:/tmp \
  smallstep/step-cli:0.28.6 step certificate create \
  --template /tmp/intermediate1.tpl --not-after=43800h \
  --ca /tmp/root_ca.pem --ca-key /tmp/root_ca.key \
  --no-password --insecure \
  "Demo Kong Intermediate1 CA" /tmp/intermediate_ca1.pem /tmp/intermediate_ca1.key
```

### Intermediate CA 2 (signed by int1)

```sh
docker run --rm \
  -v $(pwd)/ssl-certs/smallstep:/tmp \
  smallstep/step-cli:0.28.6 step certificate create \
  --template /tmp/intermediate2.tpl --not-after=26280h \
  --ca /tmp/intermediate_ca1.pem --ca-key /tmp/intermediate_ca1.key \
  --no-password --insecure \
  "Demo Kong Intermediate2 CA" /tmp/intermediate_ca2.pem /tmp/intermediate_ca2.key
```

### A leaf cert with multiple SANs

```sh
docker run --rm \
  -v $(pwd)/ssl-certs/smallstep:/tmp \
  smallstep/step-cli:0.28.6 step certificate create \
  --profile leaf --not-after=8760h \
  --ca /tmp/intermediate_ca2.pem --ca-key /tmp/intermediate_ca2.key \
  --no-password --insecure \
  --san api.kong.lan \
  --san portal.kong.lan \
  --san portal-api.kong.lan \
  --san proxy.kong.lan \
  manager.kong.lan /tmp/kong.lan.pem /tmp/kong.lan.key
```

### HAproxy bundle

```sh
cat ssl-certs/smallstep/wild.kong.lan.pem \
    ssl-certs/smallstep/intermediate_ca2.pem \
    ssl-certs/smallstep/intermediate_ca1.pem \
    ssl-certs/smallstep/root_ca.pem \
    ssl-certs/smallstep/wild.kong.lan.key \
  > ssl-certs/smallstep/combined-wild.pem
```
